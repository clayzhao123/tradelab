## 建议的整理方式

保留现有顶层入口，按职责渐进整理。下面是**建议目标**，不是本轮已经完成的迁移：

| 范围 | 现状 | 建议 |
|---|---|---|
| 前端页面 | `src/app/pages/` | 继续保留，页面逐步只承担组合与路由层职责 |
| 前端业务 | 大量逻辑在页面与统一 Context | 增加 `src/features/strategy/`、`backtest/`、`orders/` 等，放各自组件、hooks 和纯计算 |
| 前端共享 | 已有 `src/shared/` | 保留基础 HTTP、WS、错误处理；领域 API 独立分文件 |
| 后端业务 | 已有 `src/modules/` | 保留；复杂回测模块内分计算引擎与服务编排 |
| 后端存储 | 各 repository 在一个大文件中 | 在各领域目录下分 interface、mapper、memory、file、postgres 实现 |
| 文档 | 现行与历史说明并列 | 先用索引区分，后续再迁移历史文档 |
| 历史设计 | `frontend_module/` 在根目录 | 标记后再考虑归档，避免误启动 |

不要为了目录“更漂亮”同时改入口、API、存储和策略算法。每次迁移都应能清楚回答：哪项职责移动了、行为是否保持、用什么检查证明。

## 推荐的下一轮顺序

1. **先让实验可解释**：修正回测阈值的未来信息使用与年线口径，标记实际数据来源。它们影响结果可信度，优先于目录美化。
2. **再让数据可保留**：改进文件写入，决定运行账本的持久化范围，补齐数据库模式。
3. **最后降低修改成本**：抽取前端纯函数/业务 hooks，拆分回测存储与引擎，再归档设计文件和接上 CI。
